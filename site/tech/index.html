The technical build behind Lockin — a distraction-aware study companion. What it calls over the internet, where it keeps your data, and how two browsers run a synced study duel with no server between them.

01 — The shape of it

Three kinds of file, and nothing else

A web app is a website that does something rather than just showing text. Lockin is made of three kinds of file, and every one of them runs on your own computer.

HTML — the skeleton

Says there is a timer here, buttons there. Structure only, no behaviour.

CSS — the clothes

Says make it dark, round the corners, centre that. Appearance only.

JavaScript — the brain

Says when this is clicked, start counting down. All the behaviour lives here.

Everything runs in the browser. This is called client-side. There is no computer of mine running anything — GitHub hands your browser the files, and your own laptop does all the work. Which is why there is no login, no database, and nothing to attack.

02 — What an API is

A web address that answers programs, not people

A normal website sends back a page for humans. An API sends back raw data for programs — no colours, no layout, just facts. The data arrives as JSON: a labelled list like {"temperature": 31, "weather_code": 61}. My code reads the labels it needs.

Web APIs — outside services

Run by someone else, somewhere on the internet. I'm a customer. Lockin calls four addresses, and none of them needs an API key.

Browser APIs — already in Chrome

Tools built into the browser itself. Nothing is downloaded; I just call them. Most of Lockin is made of these.

Knowing the difference between those two is usually worth marks on its own.

03 — The outside world

Four addresses, no keys

Open-Meteo — weather, in two steps

1. geocoding-api.open-meteo.com/v1/search?name=Chennai
   → turns a place name into coordinates

2. api.open-meteo.com/v1/forecast?latitude=13.08&longitude=80.27
   → returns temperature and a weather code for that point

Why two calls? Weather services don't understand place names, only coordinates. The first translates Chennai into numbers; the second asks for the weather at those numbers. It returns a weather code — 61 means light rain — which the app turns into a mood that changes its entire colour scheme.

Two dictionaries — the word of the day

1. api.dictionaryapi.dev/api/v2/entries/en/petrichor   first choice
2. en.wiktionary.org/api/rest_v1/page/definition/…    backup
3. a short definition stored inside the app                 last resort

The dictionary listed in the brief was down while I built this — error 522, then no response at all. That is exactly why there are three layers. I tested the bottom layer by deliberately blocking both dictionaries. It still shows a full definition. The fallback is proven, not theoretical.

Every request carries a deadline, so a dead service can never freeze the page. The built-in definition paints immediately and is quietly upgraded if a dictionary answers — so the screen never shows a gap.

04 — A decision worth defending

Why the quotes are not from an API

They used to be. A general-purpose quotes API produced “Luxury must be comfortable, otherwise it is not luxury” — useless for a focus app. I tried to fix it with filtering before giving up on the source entirely.

AttemptPassedWhat still got through
Keyword filter14% of 420“Technological progress is like an axe in the hands of a pathological criminal.”
Strict phrase filter4.5% of 420Half were philosophy, not motivation — “Reality is merely an illusion.”

Then I tried four replacement APIs. Two were dead, two refused browsers. So the 55 quotes are curated inside the app, all about starting, effort, discipline and not stopping.

You cannot filter quality into a source that does not have it. The internet requirement is still met several times over by the weather and dictionary calls.

05 — The trap

It worked in the terminal and failed in the browser

One replacement API looked perfect. I tested it from the command line and it returned exactly what I wanted. In the real app it returned nothing at all.

zenquotes.io    HTTP 200 in curl   →   blocked in the browser
                  no access-control-allow-origin header

CORS is a security rule: a website must give permission before another website's code may read its data. Without that permission the browser refuses — to protect you. The catch is that command-line tools ignore CORS and browsers enforce it, so something can pass a test and still fail in production.

Testing an API with curl does not prove it works in a browser. This is the single most useful thing I learned building Lockin.

07 — Memory

Where your data lives, and why it survives

Everything sits in localStorage — a small box the browser gives each website, saved on your own hard drive. It survives closing the browser and restarting the machine. It is never sent to me or anyone else.

lockin.v1

Sessions, plans, minutes per day, settings, XP, achievements, head-to-head records, duels, today's quote and word.

lockin.active

The session running right now, written every couple of seconds — so an accidental refresh mid-session doesn't lose your work.

One detail worth mentioning out loud: localStorage stores text only. Objects are flattened to text going in and rebuilt coming out — like writing a filled form onto a single line and reading it back later.

The app was renamed twice during development. On first load it checks the old storage names, copies anything it finds into the new one, and deletes the old. Nobody loses their history to a rename.

08 — The centrepiece

Two laptops, one timer, no server

This is the hardest thing in the project. Normally, for two people to see the same thing, both talk to a central computer. I don't have one. So how do two laptops agree on anything?

Part one — the synced timer

The trick is to put the information inside the link. When you create a room, the app writes the room id, your name, the exact start time and the length into the web address itself. Your friend opens that link and their browser reads those details straight out of it. Both browsers now know the same start time, so both count down to the same moment using their own clocks.

I don't send the timer between them. I send the start time inside the link, and both browsers do the same subtraction. It's arithmetic, not communication — which is why it works with no server and no connection.

Part two — live stats

Seeing your friend's tab-leaves as they happen cannot be done with arithmetic. That is real information moving between two machines, and it needs a channel.

Same browser, two tabs

BroadcastChannel. Tabs of one browser can shout to each other, like people in the same room.

Two different devices

WebRTC. A direct, encrypted connection between the two browsers. Not through my server — I have none. The computers talk to each other.

How two strangers' browsers find each other

1

A mirror, not a middleman

A STUN server answers exactly one question: what does my address look like from the outside? It carries none of your data — it only helps the two find each other.

2

The handshake travels in a link

Each browser writes a description of itself — how to reach it, plus encryption keys — and the two must swap these. Normally a server relays them. I have none, so the link carries it. You send one link; their browser automatically produces a reply link; you paste it once; connected.

3

Squeezing 2,000 characters into 500

That connection description is normally about 2,000 characters — far too long to send over a chat app. But for a simple data connection almost all of it is identical every time. Only five things actually differ: two ID codes, a security fingerprint, a role, and the network addresses. I keep those five and rebuild the rest from a template on the other side.

full connection description   ~2,000 characters   too long to send
keep only what differs          ~500 characters   fits in a chat message

When the connection fails

Some mobile networks block direct connections. Then the timer still syncs — that never needed a connection — and each side sends a short result link at the end, so the duel still settles. Nothing is lost; it degrades.

The duel itself

When both finish, the scores are compared. The focus score is a formula, not a guess:

55%  how much of your planned time you actually focused
45%  focused time versus time away
−3   points for every distraction you logged yourself
     clamped to 0–100

Higher score wins. The result goes into a permanent head-to-head record against that friend — 3W 1L 0D — along with a co-study streak. Rematch is one button.

09 — The rest of the machinery

Small decisions that keep it honest

The timerRecords the clock time you started and subtracts, rather than counting ticks. Browsers deliberately slow timers in background tabs, so counting would drift and undercount. Comparing timestamps stays accurate.
DistractionsThe Page Visibility API fires the instant the page is hidden. The app adds one tab-leave and starts counting that time as “away”.
The honest limitThe browser tells me you left my page. It cannot tell me what you switched to — no website can, and that is a good thing.
Focus soundsNo audio files at all. Random numbers are generated as raw sound — that is literally what static is — then filtered into rain or lo-fi. Nothing to download, and it never loops.
Hands-freeChrome is asked for five guesses and the first that makes sense wins. Known mishearings are repaired (paws → pause, finnish → finish), and the wake word is judged by shape, because a fixed list missed “locket” and silently dropped the command.
The greetingOpen-Meteo is asked with timezone=auto, so its hour is the hour in your city, not on your device. Tested from one machine at midnight: Reykjavik said evening, Sydney late night, Chicago afternoon.
Streaks and XPPlain maths over your saved sessions — averages, counting backwards through dates, totals per weekday.
10 — Getting it online

A repository, and a free web address

The code lives in a GitHub repository — an online folder that remembers every version. GitHub Pages serves those files as a real website, free. Every time a change is pushed, the site rebuilds itself in about a minute. That is what deploying means.

No server runs the code. GitHub simply hands the browser the HTML, CSS and JavaScript, and everything happens on your machine from there.

12 — Likely questions

Answers worth having ready

“Why no framework?”

The brief required plain HTML, CSS and JavaScript — and the app doesn't need one. It is a single page with no complex shared state.

“Where is your API key?”

There isn't one, deliberately. With no backend, a key would sit in the JavaScript where anyone could read it by pressing F12.

“Is it secure?”

There is nothing to attack — no login, no server, no database, no keys. The one caution is the live study link, which contains a network address so two browsers can find each other; the app labels it and says to send it only to your partner.

“Isn't the duel a backend?”

No. The timer is arithmetic on a timestamp in a URL, and the live stats go straight from one browser to the other. No server of mine is involved at any point.

“What doesn't work everywhere?”

Voice needs Chrome or Edge — Firefox has no speech recognition at all. The app detects this and says so, and a typed command box works in every browser.

“What was hardest?”

Study Together: getting two browsers to talk with no server, and squeezing a 2,000-character connection description into a link short enough to send.
